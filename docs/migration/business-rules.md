# Velora Shared Business Rules Specification

## Overview
This specification records all shared business rules governing the Velora platform. These rules define observable product behavior across both PHP reference (`veloratrade/veloratrade`) and Modern Node.js/TypeScript implementations (`veloratrade/velora-modern`).

---

## 1. Financial & Trading Math Invariants

### 1.1 Gross PnL Calculation
- **Rule**: Gross PnL must be computed using arbitrary-precision decimal arithmetic (scale 8 minimum).
- **Formula**:
  - `buy`: `grossPnl = (exitPrice - entryPrice) * volume * contractSize`
  - `sell`: `grossPnl = (entryPrice - exitPrice) * volume * contractSize`
- **Contract Size Standard Defaults**:
  - Forex standard lot: `100,000` units
  - Gold (XAUUSD): `100` oz
  - Indices / Crypto / Commodities: `1` unit (or per instrument spec)
- **Formatting**: Output rounded and formatted to 2 decimal places in monetary API responses.

### 1.2 Net PnL Calculation
- **Rule**: Commission and swap costs reduce gross PnL.
- **Formula**: `netPnl = grossPnl - commission - swap`
- **Formatting**: Output rounded to 2 decimal places. Fits `DECIMAL(16,8)` schema constraints.

### 1.3 Risk & R-Multiple Calculation
- **Risk Formula**:
  - `buy`: `risk = (entryPrice - stopLoss) * volume * contractSize` (when `entryPrice > stopLoss`)
  - `sell`: `risk = (stopLoss - entryPrice) * volume * contractSize` (when `stopLoss > entryPrice`)
- **Invalid Risk**: If `stopLoss` is missing, `0`, or placed on the wrong side of the entry price (e.g., SL higher than entry on a buy trade), `risk` is undefined (`null`).
- **R-Multiple Formula**: When `risk > 0`, `rMultiple = netPnl / risk`. Otherwise, `rMultiple = null`.
- **Formatting**: Output formatted to 4 decimal places. Fits `DECIMAL(10,8)` schema constraints.

## 2. Authentication & Security Business Rules

### 2.1 Password Hashing & Legacy Remapping
- **Primary Algorithm**: Argon2id with recommended security parameters (memory cost >= 65536 KiB, time cost >= 3, parallelism >= 4).
- **Legacy Compatibility**: Bcrypt hashes starting with `$2y$` (generated by PHP `password_hash`) must be remapped to `$2a$` before verification with Node.js `bcryptjs`.
- **Automatic Re-hashing**: On successful login with a valid Bcrypt password, the hash must be upgraded to Argon2id in the database.

### 2.2 RBAC Authorization Isolation
- **Rule**: User Role (`users.role`) and Subscription Plan (`users.plan`) MUST be kept strictly separate.
- **Roles**:
  - `guest`: Pre-authentication state (never stored).
  - `user`: Standard registered user.
  - `admin`: Operational administrator.
  - `super_admin`: System owner / root admin.
- **Plans**: `free`, `pro`, `enterprise`.
- **Invariant**: Subscription plan NEVER grants authorization or elevates a user to an administrative role. Authorization is governed strictly by role permissions (`Role::can()` / `hasPermission()`).

### 2.3 Database Safety & Fail-Closed Behavior
- **Rule**: DB errors during authentication, rate limiting, or session verification MUST fail closed in `development` and `production` environments by throwing HTTP 503 `SERVICE_UNAVAILABLE`.
- **Test Environment Exception**: In-memory repository fallback (`MemoryStore`) is strictly prohibited in dev/prod and permitted ONLY when `NODE_ENV === 'test'`.

## 3. Localization & i18n Invariants

### 3.1 Key Parity & Catalog Integrity
- **Supported Locales**: English (`en`) and Persian (`fa`).
- **Key-Level Parity**: All keys present in `en.json` must exist in `fa.json` and vice versa. Missing or orphan keys fail the build gate.
- **Direction**: `en` catalog direction must be `ltr`; `fa` catalog direction must be `rtl`.

### 3.2 Brand Policy Preservation
- **Brand Terms**: Product brand terms `"VELORA"` and `"MetaAPI"` must NOT be translated into Persian or altered in any locale catalog.

### 3.3 Numeric Display Invariant
- **ASCII/Latin Digits**: Numeric values, trade volumes, prices, dates, and calculated metrics across all locales (including Persian `fa`) MUST use ASCII/Latin digits (`0-9`). Eastern Arabic digits (`۰-۹`) are strictly prohibited in data and API responses.
